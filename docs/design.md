# 业务与接口契约（拟实现）

**权限**：上游只建 Pull Mirror；权威仓保护 main/master，禁止直接推送，要求指定评审批准；开发者写 Fork 或授权分支。Bridge 不用管理员令牌替用户合并。每次展示、导出和写操作都按当前用户重新检查涉及仓库的权限；跨仓回执不可泄漏不可见成员。

**存储**：独立 SQLite WAL。ProjectGroup 记录组及成员；TopicChangeSet 记录 Topic、版本号与逐仓操作结果；DeliveryReceipt 记录不可覆盖的回执版本、摘要与快照位置。首版成员清单可用 JSON；另设技术表 WebhookInbox，事件投递 ID 唯一，用于去重和失败重试。服务重启后继续未完成任务。

**联调**：按项目白名单分页读取 PR，从标题或描述识别完整 `[Topic: CAD-TOL-01]`，也可手选仓库、源分支和目标分支。以仓库 ID + PR 编号去重。界面逐仓展示变更文件数、CI、冲突、审批、head SHA 和最后刷新时间。未知不是通过。批量建 PR 记录逐项结果，重试时复用已有 PR。

**合并与恢复**：每仓独立确认，检查预期 head SHA、审批与分支保护，交由 Gitea 最终裁决。请求超时先回查，不盲重试。部分成功时保留已合并项，将失败仓标红；可选择修复冲突重试，或以实际合并提交生成反向 PR，仍须人工批准。不能安全自动反向时转人工，不 reset 主干。

**证据**：内部 webhook 接收 pull_request、release，校验原始请求体 HMAC 并持久去重，异步回查 Gitea。绑定仓库、PR、实际合并 SHA 或 release 标签解析后的提交、变更清单、验证范围、执行人和时间。制品用受管根目录下的相对标识，拒绝越界路径和重解析点；先复制到受控快照再流式计算 SHA-256。未验证项目显式标记。JSON 为权威快照，Markdown 从快照生成。摘要不是防篡改保证：签名并将摘要送独立只追加存储，公开验签材料；更正只能生成关联的新版本。

|页面 / 接口|作用|
|---|---|
|GET /bridge/api/projects|项目总览、分支保护巡检、最新提交|
|POST /bridge/api/topics|按组或显式成员建单，支持幂等键|
|GET /bridge/api/topics/{id}|逐仓只读状态与部分成功摘要|

页面使用原生 ES Modules；导航只挂“多仓联调”和“交付回执”两个链接。部署时选择并验证对应版本的导航扩展点，不覆盖整套模板；注入失效时保留 `/bridge/` 独立入口。

## 已实现的保存接口

配置 Bridge 独立 SQLite 后，`POST /bridge/api/topics` 接收同源 JSON 请求及 `Idempotency-Key`。请求字段为 `project_id`、`topic` 和可选的 `members`；省略 `members` 表示使用整组，显式指定时每项填写 `repository_id`，可同时填写 `source_branch` 和 `target_branch`。建单时每个成员仓都必须在项目白名单内，且创建者有读取权限。建单不创建分支或 PR。

首次保存返回 `201`，同用户重试相同请求返回原联调单（`200`）；同用户用同一个键提交不同内容返回 `409`。`GET /bridge/api/topics/{id}` 返回固定成员、版本、建单人和即时查询结果；任一成员不再可访问时，整张单返回与不存在相同的 `404`。

### 同仓分支建 PR

显式开启后，`POST /bridge/api/topics/{id}/pulls` 接收同源 JSON `{"confirm":true,"member_ids":[1,2]}`，一次选 1–8 个已填写源、目标分支的成员。当前只支持同一成员仓里的两个分支；跨 Fork 提交仍待实现。不可写、镜像或归档仓不会提交，当前请求以 `write_denied` 返回不可写成员 ID，不覆盖已有操作结果。

处理前按仓 ID、分支组合和 Topic 查找已有 PR。成功时记录关联的 PR 编号，失败按仓记录，联调单版本随结果变更递增。Gitea 明确拒绝时，可以修复后重试。发请求前先写入“结果待核对”；超时、断线或重启后，用户重试只回查 Gitea，不再发创建请求。若仍无法确认，保持待核对，先在 Gitea 人工检查。不会自动合并、推送分支或申请审批。

### 逐仓确认合并

开启 `enable_merge` 后，单仓合并接口接收同源 JSON `{"confirm":true,"expected_head":"完整提交 SHA"}`。只操作已关联的同仓 PR；Bridge 重新核对 PR 身份、目标分支、当前提交、正式评审及当前用户权限。目标分支必须受保护、至少要求一人批准，且当前用户不得直接推送。Gitea 最终检查指定评审人、必跑状态等规则；Bridge 固定用普通 merge 方式，将预期提交传给 Gitea，不请求强制合并、自动合并或删除源分支。

Bridge 在发出合并前持久记录待核对状态。同一个仓库的同一个 PR 即使出现在多张联调单，待核对时也不会发第二次请求。`{"reconcile":true}` 只读 Gitea 并更新本地证据；只有回查到实际合并 SHA、执行人与时间才显示已核验。Gitea 明确拒绝则保留逐仓受阻原因，修复后需重新确认。回查仍不确定时保留待核对，不自动重发；可在 Gitea 人工核对。一个仓失败不会撤销其他仓的合并。

### 反向 PR

开启 `enable_revert` 后，接口接收 `{"confirm":true,"expected_merge":"已核验的完整合并 SHA"}`。当前仅自动处理仍处于目标分支顶端、第二父提交能和原 PR 核对的普通双亲合并；只处理小批量、常规模式的文件。目标分支已前进、非普通合并、超出读取上限或无法验证内容，转人工处理。

Bridge 根据实际合并提交和第一父提交的树差异，仅向独立 `bridge-revert-…` 分支提交逆向改动，再确认该分支的父提交是实际合并 SHA，且结果树等于合并前。通过后才开 PR，不 reset、强推、删除分支或自动合并。PR 保留 Gitea 原有审批和检查规则。跨联调单共享逐阶段记录，失败或断线不重复发送同一阶段的写请求；如果分支已核验但 PR 尚未提交，可在用户再次确认后继续。`{"reconcile":true,"expected_merge":"已核验的完整合并 SHA"}` 只做回查，不写 Gitea。

### Webhook 与回查

独立回环监听先校验原始请求体 HMAC-SHA256，再将投递 UUID、请求体摘要、白名单仓 ID 和对象 ID 持久入队。同一 ID 同一内容返回 `202`，复用同一 ID 但内容变化返回 `409`；不保存原始请求体。队列最多积压 4096 项；失败延迟重试，进程中断后租约到期可继续，观察结果只记一次。应定期检查积压及数据库体积；尚无自动清理或管理网页。

事件只当作提示，不信任其中的状态、SHA 或执行人。工作进程仅用只读令牌回查当前 Gitea 状态，保存带观察时间的独立快照，不将迟到事件写回联调单。合并读取实际合并 SHA、执行人与时间；发布按发布 ID 取标签，再核对实际提交。数据暂不展示给浏览器，不算已签发回执；后续签发仍要按当前用户重新验证访问权限。
