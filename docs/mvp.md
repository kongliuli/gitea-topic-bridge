# 首版实施设计：只读联调看板

当前版本的项目总览与保护巡检见[业务设计](design.md#项目总览与保护巡检)。

首版回答一个问题：**同一个需求在哪些仓库改了，现在各自到哪一步？** 建 PR、审批和合并仍在 Gitea 完成。Bridge 不写入 Gitea，也暂不签发交付回执。本文只定义首个可交付阶段，不替代完整业务设计。

## 操作流程

1. 从 `/bridge/` 进入，以自己的 Gitea 账号登录。
2. 选择预设项目组，输入编号，例如 `CAD-TOL-01`。项目组和仓库白名单由部署配置管理。
3. Bridge 用当前用户的授权，分页读取开放与关闭的 PR，匹配标题或正文里的完整 `[Topic: CAD-TOL-01]`，让已经合并的项也能出现。按仓库 ID 和 PR 编号去重；同仓有多条则全部展示。
4. 查看逐仓结果，点链接回原 PR。刷新重新从 Gitea 读取，不拿旧结果冒充本次查询。

切换项目组或改动需求编号后，页面清除上一组结果和操作入口。查询新条件后才显示对应结果。

## 页面与接口

|入口|首版行为|
|---|---|
|`/bridge/`|项目组选择、编号输入、逐仓结果。链接遵循规范入口，不从请求 Host 生成。|
|`GET /bridge/api/projects`|只列出用户至少能查看一个成员仓的组，不返回隐藏成员或未过滤的统计。|
|`GET /bridge/api/topics/lookup?project_id=…&topic=…`|即时查询，不持久化联调单。会话失效要求重新登录；项目组不存在与不可见给出相同响应。|

- 编号区分大小写，限 1–64 位 ASCII 大写字母、数字或短横线，首字符必须为字母或数字。
- 先应用白名单，再检查当前用户权限。无法确认可见的仓不返回；权限检查服务异常时给通用错误，不使用旧权限放行。只有确认可见的仓才显示逐仓查询失败。
- 每仓区分“已查完”“查询失败”“未查完”。限制查询时间、并发和分页量；只在可见范围查完且没有命中时显示“未找到匹配”，不把失败或超时当作无匹配。
- 分开显示 PR 生命周期、CI、冲突、审批、head SHA、变更文件数与读取时间。拿不到的字段显示“未知”，不判断整组可合并。
- 只为本次查询中最多 32 条命中 PR 补查详细状态。CI 是目标仓中该 head SHA 已报告的检查，不代表必跑项齐全。只统计当前提交、不失效、不撤销的正式评审；评审数量不代表满足分支保护。Gitea v28.4.0 的 `mergeable=false` 无法区分冲突、草稿、检查尚未完成及检查出错，此时显示“暂不可合并，原因未知”。

## 实施顺序

1. **先核对 Gitea**：在测试实例用普通账号验证登录授权、私有仓隔离、分页和 PR 字段。记录实际版本与验证结果；拿不到的字段保留“未知”。
2. **跑通一条路径**：完成登录、项目组列表、Topic 查询和逐仓展示。令牌留在服务端；此阶段不建回执表和后台任务表。
3. **验收只读首版**：用三个可见测试仓分别覆盖已合并、开放且有冲突、无匹配；加一个隐藏仓测试不泄漏。另测同仓多个 PR、分页未查完、权限撤销、会话失效和上游故障。
4. **再加写入能力**：先持久化联调单，再实现逐仓建 PR 和人工确认合并；回执、签名与失败恢复单独验收。每个阶段过验收后再更新 README 的交付状态。
